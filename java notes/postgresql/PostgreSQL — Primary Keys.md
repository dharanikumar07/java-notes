## 1. What is a Primary Key?

A **Primary Key** is a column (or combination of columns) that uniquely identifies each row in a table.

**Rules:**

- Must contain unique values.
    
- Cannot contain `NULL`.
    
- A table can have only **one primary key constraint**.
    
- A primary key can consist of one column or multiple columns.
    

### Example

```
CREATE TABLE students (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100)
);
```

|id|name|
|---|---|
|101|Ravi|
|102|Priya|
|103|Arun|

Here, `id` uniquely identifies every student.

**Invalid values:**

- Duplicate `id` → rejected.
    
- `NULL` as `id` → rejected.
    

### Diagram

```
STUDENTS TABLE
┌─────┬────────┐
│ id  │ name   │
├─────┼────────┤
│ 101 │ Ravi   │
│ 102 │ Priya  │
│ 103 │ Arun   │
└─────┴────────┘
   ↑
Primary Key
Uniquely identifies each row
```

## 2. Why Do We Need a Primary Key?

1. **Uniqueness** — prevents duplicate identifiers.
    
2. **Identification** — identifies a specific row.
    
3. **Relationships** — other tables can reference it using foreign keys.
    
4. **Data integrity** — prevents missing or duplicate primary-key values.
    

Example:

```
SELECT * FROM students
WHERE id = 102;
```

The query retrieves Priya's row using its unique identifier.

## 3. Types of Primary Keys

### A. Natural Key

A natural key uses existing real-world data to identify a record.

Examples:

- Email address
    
- Passport number
    
- License plate number
    

```
CREATE TABLE users (
    email VARCHAR(255) PRIMARY KEY,
    name VARCHAR(100)
);
```

**Disadvantages:**

- Real-world values may change.
    
- Values may be reassigned or reused.
    
- Sensitive information may be exposed unnecessarily.
    
- Longer keys can make relationships more cumbersome.
    

### B. Synthetic (Surrogate) Key

A synthetic key is an artificial identifier created specifically for the database.

Examples: `1`, `2`, `3`, or a UUID.

```
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email VARCHAR(255),
    name VARCHAR(100)
);
```

**Advantages:**

- Independent of business data.
    
- Remains stable when email or name changes.
    
- Easy to reference from other tables.
    

**Best practice:** A numeric surrogate primary key is a good default for many PostgreSQL tables.

## 4. BIGINT vs INTEGER

|Type|Storage|Range|
|---|---|---|
|`INTEGER`|4 bytes|−2.1 billion to +2.1 billion approx.|
|`BIGINT`|8 bytes|−9.22 quintillion to +9.22 quintillion approx.|

**Why choose BIGINT?**

- Provides a much larger identifier range.
    
- Reduces the risk of exhausting IDs in high-volume systems.
    
- Uses more storage than `INTEGER`.
    

For tables expected to grow significantly, `BIGINT` is a sensible default. `INTEGER` is also valid when its range is sufficient.

## 5. Automatically Generated Primary Keys

Recommended syntax:

```
CREATE TABLE employees (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

### How it works

```
INSERT employee
       ↓
PostgreSQL generates ID
       ↓
1, 2, 3, 4 ...
       ↓
Each row gets an identifier
```

Insert a row:

```
INSERT INTO employees (name)
VALUES ('Ravi');
```

PostgreSQL automatically generates the `id`.

**Important:**

- `GENERATED ALWAYS AS IDENTITY` normally prevents explicitly supplying an ID.
    
- `GENERATED BY DEFAULT AS IDENTITY` generates an ID when one is not supplied, but permits an explicit ID.
    
- Identity values can have gaps; they are not guaranteed to be consecutive.
    
- `IDENTITY` is the modern SQL-standard alternative to PostgreSQL's older `SERIAL` convention.
    

## 6. What Is a UUID Primary Key?

UUID stands for **Universally Unique Identifier**.

Example:

```
0199a123-4567-7abc-8def-123456789012
```

UUIDs are useful when IDs must be generated independently by multiple services or clients without asking one central database for an ID first.

### UUID Versions

- **UUID v4** — random UUID.
    
- **UUID v7** — time-ordered UUID, generally better suited to index locality than random v4 UUIDs.
    

UUID v7 is not automatically faster in every workload, and UUIDs consume more storage than `BIGINT`.

Use UUID when distributed ID generation is important; otherwise, `BIGINT` is a straightforward default.

## 7. What Is a Composite Primary Key?

A composite primary key uses two or more columns together to identify a row uniquely.

Example:

```
CREATE TABLE team_members (
    author_id BIGINT,
    team_id BIGINT,
    PRIMARY KEY (author_id, team_id)
);
```

Here, the **combination** of `author_id` and `team_id` must be unique.

|author_id|team_id|Valid?|
|---|---|---|
|1|10|Yes|
|1|20|Yes|
|1|10|No — duplicate combination|

### Alternative: Single Primary Key + UNIQUE

```
CREATE TABLE team_members (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    author_id BIGINT NOT NULL,
    team_id BIGINT NOT NULL,
    UNIQUE (author_id, team_id)
);
```

Now:

- `id` is the primary key.
    
- `UNIQUE (author_id, team_id)` prevents duplicate memberships.
    

**Important:** Composite primary keys are valid and useful in some designs. A separate surrogate key is often convenient when other tables need to reference the row.

## 8. Primary Key vs UNIQUE

|Primary Key|UNIQUE Constraint|
|---|---|
|One primary key constraint per table|Multiple unique constraints allowed|
|Cannot contain `NULL`|By default, allows multiple `NULL` values in PostgreSQL|
|Main row identifier|Enforces additional uniqueness rules|

Example: `id` can be the primary key, while `email` has a `UNIQUE` constraint.

## 9. Primary Key vs Foreign Key

- **Primary Key:** Identifies a row in its own table.
    
- **Foreign Key:** References a primary key or another eligible unique key in a different or the same table.
    

```
STUDENTS                 ORDERS
┌─────┬───────┐          ┌────┬────────────┐
│ id  │ name  │          │ id │ student_id│
├─────┼───────┤          ├────┼────────────┤
│ 101 │ Ravi  │◄─────────│  1 │    101     │
│ 102 │ Priya │          │  2 │    101     │
└─────┴───────┘          └────┴────────────┘
    Primary Key              Foreign Key
```

The `student_id` column in `orders` references `students.id`.

## 10. Interview Revision

- **Primary key:** Uniquely identifies each row; cannot be `NULL`.
    
- **Natural key:** Uses real-world data.
    
- **Surrogate key:** Artificial database identifier.
    
- **BIGINT:** 8-byte integer with a very large range.
    
- **IDENTITY:** Automatically generates numeric identifiers.
    
- **UUID v7:** Time-ordered identifier useful for distributed generation.
    
- **Composite key:** Uniqueness depends on multiple columns.
    
- **UNIQUE constraint:** Enforces additional uniqueness rules.
    

**Remember:** A primary key identifies a row; a foreign key connects related rows; a unique constraint prevents duplicate business values.
